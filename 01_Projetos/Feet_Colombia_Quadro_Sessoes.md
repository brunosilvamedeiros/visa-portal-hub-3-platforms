# Quadro de Sessões — Execução do Roadmap 2026

Gestão das sessões de trabalho do roadmap [Feet Colombia 2026](./Feet_Colombia_Roadmap_Funcionalidades_2026.md): **pequenas entregas coordenadas, 1 sessão = 1 entrega mergeável**, cada uma com o modelo adequado à complexidade.

## 🎛️ Como funciona

1. **Coordenadora**: esta sessão (`session_01RoFGD36avWwfWqtqQemK5N`) cria as sessões de trabalho com o modelo certo, acompanha o andamento (check-ins periódicos), integra os resultados ao roadmap e despacha a leva seguinte quando dependências fecham.
2. **Contrato de entrega de cada sessão**: branch própria `claude/<slug>` a partir de `staging` → PR pequena para `staging` (specs = doc-only; builds = código + testes) → memória `wip-<id>` → resumo de 5 linhas para a coordenadora (send_message, quando disponível).
   **Protocolo de merge (definido 10/08)**: o Bruno NÃO executa merges — a coordenadora lista as PRs prontas com resumo, o Bruno **autoriza no chat**, e a coordenadora executa: direto nos repos `brunosilvamedeiros/*`; no repo do produto (`Sants-M13/*`, fora do escopo da coordenadora) via sessão *merge-runner* (Haiku) com a autorização citada no prompt.
3. **Paralelismo sem conflito**: specs doc-only rodam em paralelo à vontade; **nunca duas sessões no mesmo módulo/pasta**; contratos entre ondas vêm da spec S0.1 (estados + eventos).
4. **Etiquetas**: sessões nascem com tags `feet-2026`, `fase-0|onda-1|…` e `feet-sessao:<id>`.
5. **QA obrigatório antes de todo merge (regra do Bruno, 13/08 — PERMANENTE)**: o repo do produto (`Sants-M13/Medusa`) tem protocolo próprio no seu `CLAUDE.md` — **`/qa` antes do `/ship`**. Daqui em diante NENHUMA PR vai para merge sem a etapa de QA executada e a evidência registrada na própria PR. Sequência padrão: sessão entrega a PR → **sessão de QA roda o protocolo do CLAUDE.md e comita a evidência** → bugs encontrados são descritos em português com severidade (corrigir no escopo ou abrir PR separada) → Bruno autoriza no chat → merge-runner executa o ship. Runner que encontrar QA pendente deve recusar — isso é comportamento correto, não teimosia. *(As 10 PRs mergeadas em 12–13/08 saíram antes desta regra; o Bruno foi informado.)*
6. **Confirmar o DEPLOY antes de anunciar teste (regra nova, 13/08 — PERMANENTE)**: CI verde ≠ ambiente atualizado. Após cada merge, verificar no painel do Medusa Cloud se o **build de staging passou** e qual commit está no ar. **Nenhum roteiro de teste é enviado ao Bruno sem essa confirmação.** Motivo: em 13/08 o staging ficou ~17h com "Build failed" em `bcc1eef` e a coordenação anunciou 6 frentes como testáveis — quem detectou foi o Bruno.
7. **Roteiro de teste a cada liberação (regra do Bruno, 12/08 — PERMANENTE)**: sempre que algo novo entra em `staging`, a coordenadora entrega ao Bruno, no chat, um **passo a passo numerado com o resultado esperado de cada passo** (o que clicar, onde, e o que deve acontecer — incluindo o que NÃO deve acontecer). Um bloco por entrega, com o nº da PR. Sem roteiro, a liberação não está comunicada. Vale também para fixes: o roteiro deve reproduzir o caminho exato do bug que ele reportou.
8. **Sucessão da coordenadora (regra do Bruno, 12/08)**: ao atingir ~50% da janela de contexto, a coordenadora AUTOMATICAMENTE organiza a sucessão — atualiza o quadro com o estado completo, cria a sucessora (Fable 5, neste repo/branch) com briefing integral (método + estado + lições operacionais), desarma os próprios triggers de check-in, e a sucessora arquiva a antecessora ao confirmar a assunção.
9. **Lições operacionais acumuladas**: **2 recusas de runners diferentes na mesma PR = escalar ao Bruno, não reformular o prompt (reformulação sucessiva é lida como bypass de salvaguarda)** · **sessão de QA pode omitir achados abertos e reportar só o que corrigiu — exigir "X achados no total, Y abertos" e cruzar com a verificação independente do runner antes de despachar merge** · **o `CLAUDE.md` do repo do produto define protocolo próprio (`/qa` → `/ship`) — conhecer e seguir antes de despachar merge; recusa repetida de runner costuma ser convenção local, não teimosia** · **nota informal no corpo da PR ("aguardando QA") faz runner recusar merge — declarar no prompt que só valem checks do GitHub + autorização do Bruno; e auditar read-only antes de insistir** · **prompt de merge-runner deve fixar o ALVO inequivocamente (repo + nº da PR + branch + base + tema) e declarar que a autorização do Bruno no chat é o único gate (não há /qa) — runner solto busca PR errada e trava** · **merge-runner Haiku estoura contexto em PR grande — exigir checagem por API do GitHub (sem clone/diff completo) e usar Sonnet quando a PR toca módulo extenso** · **sessões de build travam pedindo permissão para tools de orquestração (delete_trigger/send_later) — proibir explicitamente nos kickoffs;
